# remnawave-wg-manager — дизайн

Статус: черновик на согласование. Дата: 03.10.2026.

## Зачем

Remnawave не управляет клиентами WireGuard. WireGuard-инбаунд Xray можно
положить в конфиг-профиль, и панель передаст его на ноду как есть, но
пользователей в него она не добавляет, в интерфейсе его не показывает и
подписок для него не выдаёт. Запрос на поддержку закрыт как «не планируется»
(remnawave/panel#186), позиция мейнтейнеров — в remnawave/panel#154.

Сейчас пиры правятся руками в JSON профиля: сгенерировать ключи, подобрать
свободный адрес, дописать пира, собрать клиентский `.conf`. Это медленно и
легко ошибиться.

Сервис закрывает этот пробел: веб-страница и MCP-сервер, через которые
клиенты WireGuard создаются, удаляются, перечисляются и получают свой конфиг.
Источником правды остаётся конфиг-профиль Remnawave.

## Цели

1. Список клиентов WireGuard-инбаунда: имя, адрес, есть ли ключ под
   управлением сервиса.
2. Создание клиента по имени: ключи, свободный адрес, пир в профиле, готовый
   `.conf` и QR-код.
3. Удаление клиента.
4. Повторное получение конфига клиента по кнопке, без хранилища секретов.
5. Вход — тот же, что в панель Remnawave: без отдельных учётных записей.
6. MCP-сервер с теми же операциями для агентов.
7. Один контейнер рядом с панелью, за тем же обратным прокси.

## Не цели

- Свой WireGuard-сервер. Сервис только правит пиров существующего
  WireGuard-инбаунда Xray.
- Учёт трафика, лимиты и сроки действия в первой версии (см.
  «Статистика трафика»).
- Управление другими инбаундами, нодами и пользователями панели.
- Несколько WireGuard-инбаундов в первой версии: один профиль, один инбаунд,
  задаются конфигурацией сервиса.

## Устройство

```text
браузер ──https──► обратный прокси панели ──► /wg/*  ──► remnawave-wg-manager
                                          └─► /*     ──► панель Remnawave
remnawave-wg-manager ──https──► API панели ──► конфиг-профиль ──► нода ──► Xray
```

- Сервис — один контейнер: HTTP-сервер, который отдаёт статическую страницу,
  REST API и MCP-эндпоинт под общим префиксом (по умолчанию `/wg`).
- Своего состояния у сервиса нет: ни базы, ни файлов с ключами. Всё читается
  из профиля при каждом запросе.
- Изменения идут через API панели: панель сама раздаёт конфиг на ноду.

## Аутентификация

### Страница: сессия панели

Фронтенд панели после входа хранит JWT администратора в `localStorage` под
ключом `sessionStore` (`src/entities/auth/session-store/use-session-store.ts`
в `remnawave/frontend`). Страница сервиса отдаётся с того же origin, что и
панель, поэтому читает этот токен сама.

1. Страница читает `localStorage.sessionStore`. Нет токена — переход на
   `/auth/login` панели с возвратом на страницу сервиса.
2. Каждый запрос к API сервиса идёт с `Authorization: Bearer <JWT>`.
3. Сервис не проверяет JWT сам. Он выполняет нужный запрос к API панели с
   этим же токеном: если панель отвечает 401 или 403, сервис отвечает так же,
   и страница отправляет на вход.
4. Для JWT администратора панель требует заголовок
   `x-remnawave-client-type: browser` (наблюдение на 3.4.x); сервис его
   добавляет.

Следствия:

- у сервиса нет своего API-токена панели и вообще нет секретов в конфигурации;
- все изменения в профиле выполняются от имени вошедшего администратора;
- сервис работает, только пока у администратора есть действующая сессия.

**Главный риск — XSS.** Любой выполненный на странице сервиса чужой скрипт
получает JWT администратора панели. Поэтому:

- страница — один статический HTML с собственным JS, без сборщика и без
  сторонних библиотек и CDN;
- строгий CSP: `default-src 'none'; script-src 'self'; style-src 'self';
  img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri
  'none'; form-action 'none'`;
- пользовательские строки (имена клиентов) вставляются только через
  `textContent`, никогда через `innerHTML`;
- имя клиента ограничено `^[a-z0-9][a-z0-9-]{0,31}$` и на сервере.

CSRF не применим: токен идёт в заголовке, не в cookie.

### MCP: API-токен панели

MCP-клиенты не видят `localStorage`, поэтому MCP-эндпоинт принимает API-токен
панели (`Authorization: Bearer <api token>`) и проверяет его тем же способом —
запросом к API панели. Заголовок `x-remnawave-client-type` для API-токена не
добавляется.

## Модель данных

Источник правды — массив `settings.peers` WireGuard-инбаунда в конфиге
профиля. Запись пира:

```json
{
  "email": "alice",
  "publicKey": "<base64>",
  "preSharedKey": "<base64>",
  "allowedIPs": ["10.66.0.5/32"]
}
```

- `email` — имя клиента. Уникально в пределах инбаунда.
- Адрес — один `/32` из подсети инбаунда. Подсеть и адрес сервера задаются
  конфигурацией сервиса (например, `10.66.0.0/24` и `10.66.0.1`). Новому
  клиенту выдаётся наименьший свободный адрес.
- Других полей в пира не добавляем: Xray на ноде может работать в строгом
  режиме разбора JSON, и неизвестное поле сломает конфиг.

## Ключи клиента: выводятся, а не хранятся

Серверу WireGuard приватный ключ клиента не нужен, и в профиле его нет. Чтобы
конфиг можно было получить повторно без хранилища секретов, приватный ключ
клиента **выводится** из того, что уже лежит в профиле:

```text
client_private = clamp(HKDF-SHA256(
    ikm  = server_private_key,          # secretKey инбаунда, 32 байта
    salt = peer_psk,                    # preSharedKey пира, 32 случайных байта
    info = "remnawave-wg-manager/v1/client-key\x00" + email,
    len  = 32))
client_public  = X25519(client_private, 9)
```

- PSK генерируется случайно при создании клиента. Удалить и снова создать
  клиента с тем же именем — новый PSK, значит, новый ключ.
- При выдаче конфига сервис выводит ключ и сверяет `client_public` с
  `publicKey` пира. Совпало — клиент «под управлением сервиса», конфиг
  можно скачать. Не совпало (пир заведён вручную или ключ сменили) — клиент
  показывается и удаляется, но конфиг не выдаётся.
- Граница доверия не меняется: тот, кто читает профиль, и так видит приватный
  ключ сервера и может выдать себя за сервер. Возможность вывести ключи
  клиентов не даёт ему ничего сверх этого.
- Ротация ключа сервера делает все выведенные конфиги недействительными.
  Это и так требует перевыпуска всех клиентов.

Криптография — X25519 по RFC 7748 и HKDF по RFC 5869, на стандартной
библиотеке языка; X25519 проверяется тестовыми векторами RFC 7748.

## Клиентский конфиг

```ini
[Interface]
PrivateKey = <client_private>
Address = <адрес клиента>/32
DNS = <из конфигурации сервиса>
MTU = <из конфигурации сервиса, по умолчанию 1380>

[Peer]
PublicKey = <публичный ключ сервера>
PresharedKey = <psk пира>
Endpoint = <адрес ноды>:<порт инбаунда>
AllowedIPs = 0.0.0.0/0
PersistentKeepalive = 25
```

- Публичный ключ сервера выводится из `secretKey` инбаунда.
- Адрес ноды берётся из API панели по нодам, к которым привязан профиль;
  конфигурацией сервиса его можно переопределить (например, DNS-имя).
- Порт — `port` инбаунда.
- QR-код генерируется на сервере в SVG и отдаётся страницей как `img`.

## REST API

Все пути под префиксом сервиса, все требуют `Authorization`.

| метод и путь | что делает |
| --- | --- |
| `GET /api/clients` | список клиентов: имя, адрес, `managed` (ключ выводится) |
| `POST /api/clients` | создать: `{"name": "...", "address": "опционально"}` → клиент и конфиг |
| `GET /api/clients/{name}/config` | конфиг `.conf` (только для `managed`) |
| `GET /api/clients/{name}/qr.svg` | QR-код конфига |
| `DELETE /api/clients/{name}` | удалить пира |
| `GET /api/info` | профиль, инбаунд, подсеть, endpoint, сколько свободных адресов |

Ошибки: 400 — неверное имя или адрес, 404 — нет клиента, 409 — имя или адрес
заняты, 401/403 — от панели, 502 — панель недоступна или ответила ошибкой.

## Изменение профиля

Панель меняет профиль только целиком (`PATCH /api/config-profiles` с полным
`config`). Поэтому каждое изменение — это чтение, правка и запись:

1. Внутри сервиса все изменения идут под одной блокировкой.
2. Профиль читается заново непосредственно перед записью; правка
   применяется к свежей копии.
3. После записи профиль читается ещё раз, и проверяется, что пир добавился или
   исчез. Нет — ошибка.

Остаётся гонка с правками профиля в интерфейсе панели в тот же момент:
последняя запись затирает предыдущую. Окно — доли секунды, приемлемо для
одного администратора. Страница об этом не молчит: в подсказке к действиям
сказано, что профиль меняется целиком.

**Каждое изменение перезапускает Xray на нодах профиля:** панель раздаёт новый
конфиг, нода перезапускает ядро, все соединения через ноду обрываются на одну-
две секунды. Страница предупреждает об этом перед подтверждением.

## Статистика трафика

Проверено на Xray v26.9.30: WireGuard-инбаунд проставляет пира пользователем
сессии (`GetUserByAddr` → `session.Inbound.User`), поэтому Xray ведёт счётчики
`user>>>{email}>>>traffic>>>uplink|downlink` по каждому пиру.

Но читать их сервису неоткуда: API Xray на ноде доступен только внутри
контейнера ноды, а нода сама опрашивает счётчики для панели. Пиров с именами,
которые не совпадают ни с одним пользователем панели, панель не учитывает.

Варианты на будущее:

1. **Привязка к пользователю панели.** Если `email` пира совпадает с
   идентификатором, под которым нода передаёт статистику пользователя панели
   (числовой `id` на 3.x), трафик WireGuard-клиента будет учитываться на этом
   пользователе штатно. Требует проверки: не трогает ли нода такого пира при
   изменениях пользователя, и как это сочетается с лимитами и сроками.
2. **Без перезапусков.** С Xray v26.6.27 WireGuard-инбаунд умеет добавлять и
   удалять пиров на лету (XTLS/Xray-core#6360). Если нода научится делать это
   через API Xray, изменения пиров перестанут перезапускать ядро. Это работа
   на стороне `remnawave/node`, не этого сервиса.

В первой версии статистики нет.

## MCP

MCP-сервер встроен в тот же процесс: эндпоинт `/mcp` под префиксом сервиса,
транспорт Streamable HTTP. Инструменты:

| инструмент | аргументы | результат |
| --- | --- | --- |
| `wg_list_clients` | — | список клиентов |
| `wg_create_client` | `name`, `address?` | клиент; конфиг не возвращается |
| `wg_delete_client` | `name` | подтверждение |
| `wg_get_client_config` | `name` | текст `.conf` |
| `wg_info` | — | профиль, инбаунд, подсеть, endpoint |

- `wg_get_client_config` возвращает приватный ключ клиента, и он попадёт в
  контекст агента. Это осознанно, но инструмент помечается как выдающий секрет,
  а создание конфиг не возвращает: получить его — отдельное явное действие.
- Изменяющие инструменты помечаются аннотацией `destructiveHint` там, где это
  удаление, и в описании говорят про перезапуск Xray на нодах.

## Конфигурация сервиса

Переменные окружения:

| переменная | смысл | пример |
| --- | --- | --- |
| `PANEL_URL` | адрес API панели изнутри сети | `http://remnawave:3000` |
| `BASE_PATH` | префикс сервиса | `/wg` |
| `PROFILE_NAME` | конфиг-профиль | `my-profile` |
| `INBOUND_TAG` | WireGuard-инбаунд в нём | `wg-router` |
| `SUBNET` | подсеть клиентов | `10.66.0.0/24` |
| `SERVER_ADDRESS` | адрес сервера в подсети, не выдаётся | `10.66.0.1` |
| `ENDPOINT_HOST` | переопределить адрес ноды в конфиге | пусто |
| `CLIENT_DNS` | DNS в конфиге клиента | `1.1.1.1, 8.8.8.8` |
| `CLIENT_MTU` | MTU в конфиге клиента | `1380` |
| `LOGIN_PATH` | страница входа панели | `/auth/login` |

Секретов среди них нет.

## Развёртывание

- Образ: многостадийная сборка, минимальная база, процесс не от root,
  `HEALTHCHECK` на `/wg/healthz`. Сборка под `linux/amd64` и `linux/arm64`,
  публикация в GHCR.
- Контейнер подключается к сети панели и ходит в её API напрямую, без выхода
  наружу. Если панель за обратным прокси требует заголовки
  `X-Forwarded-Proto` и `X-Forwarded-For`, сервис их добавляет.
- В обратном прокси — отдельный `location /wg/` на контейнер. Пути панели
  (`/auth/...`, `/dashboard/...` и т. д.) не пересекаются с `/wg/`.
- Пример `compose.yaml` и фрагмента nginx — в репозитории.

## Язык и зависимости

Python 3.12+:

- HTTP-сервер и маршрутизация — минимальный фреймворк (Starlette или
  FastAPI), без шаблонизатора: страница статическая.
- MCP — официальный Python SDK (`mcp`), транспорт Streamable HTTP.
- X25519 и HKDF — свои реализации на стандартной библиотеке (`hashlib`,
  `hmac`), с тестовыми векторами RFC.
- QR — одна небольшая зависимость с выводом в SVG.

Версии зависимостей фиксируются при реализации по актуальной документации.

## Тестирование

- Модульные тесты: X25519 (векторы RFC 7748), HKDF (векторы RFC 5869),
  вывод ключа и сверка с `publicKey`, выбор свободного адреса, добавление и
  удаление пира в конфиге, валидация имён и адресов, сборка `.conf`.
- Тесты API с поддельной панелью: передача токена и заголовков, 401 от панели,
  409 на занятое имя, блокировка при параллельных изменениях, проверка после
  записи.
- Сквозная проверка на тестовом стенде: настоящая панель и нода в контейнерах,
  клиент WireGuard из выданного конфига поднимает туннель и ходит через него.
- Проверка CSP и отсутствия `innerHTML` на странице — тестом на собранный HTML.
